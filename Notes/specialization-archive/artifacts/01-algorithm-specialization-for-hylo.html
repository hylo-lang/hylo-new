§The ask

What we want to be able to write

Two implementations of one algorithm, differing only in what they assume about their operand, and a compiler that picks the better one wherever it is applicable — the thing the STL gets from tag dispatching and C++20 gets from concept subsumption. 

// the generic implementation — a linear scan
fun lower_bound<C is BidirectionalCollection>(in c: C, _ x: C.Element) -> C.Position

// the specialized one — a binary search
fun lower_bound<C is RandomAccessCollection>(in c: C, _ x: C.Element) -> C.Position

// …and one hand-tuned for a single type
given <T> => Array<T> is lower_bound { … }

Docs/State-of-Generics.md already lists this under Known limitations → Specialization, and offers only a manual, per-call-site override.

⊩Ground truth

Four things that are true today

Established by building the compiler and reading the IR it emits, not by reading the source alone.

Generics are compiled by existentialization, not monomorphization

Every generic function receives its witnesses as runtime values. So specialization cannot be a code-generation trick: the implementation a generic function uses must be reachable from a witness its caller hands it. That single constraint determines the whole design.

Sources/FrontEnd/IR/IREmitter+Deploymorphization.swift

Implicit resolution ranks by derivation size, which is orthogonal to specificity

The search stops at the first depth that yields a result, then keeps the lexically closest. Two overlapping givens at equal depth are an ambiguity error; a more specific given one step deeper is never reached at all.

Typer.takeSummonResults — probes e1, e6

The encoding that works is already expressible — just unusable at scale

Naming the algorithm as its own trait and constraining clients on that does carry the specialized implementation across a generic boundary. It is Siek and Lumsdaine's CopyRange idiom, and it works in Hylo today. Every overlap is simply an ambiguity error.

probes e4, lb

Two functions differing only in their context clause already parse

The compiler accepts them and builds an overload set; the call is merely ambiguous. Concept-based overloading is one ranking rule away.

≺The rule

Order givens by entailment, not by size

For givens g = ∀X̄. C̄g ⇒ Hg and g′ = ∀Ȳ. C̄g′ ⇒ Hg′: g is at least as specific as g′ when some substitution ρ of Ȳ makes ρ(Hg′) = Hg and, under the assumptions C̄g, every requirement in ρ(C̄g′) is derivable.

This is C++20's subsumption, G's “callable from”, and Rust RFC 1210's apply(I) ⊆ apply(J), transposed onto Hylo's givens. Two properties make it fit Hylo rather than fight it.

  • It is stratified. Specificity is defined in terms of derivability, never in terms of the choice rule — so the ordering can never depend on itself.
  • It subsumes the existing escape hatch. A local given with a closed head and an empty context entails everything and is entailed by nothing, so it is automatically maximal. The manual override documented in State-of-Generics.md keeps working, and now for a principled reason.
  • It covers the whole chain in one mechanism. Array ≺ RandomAccessCollection ≺ BidirectionalCollection: a more concrete head and a finer context are both ordered by the same definition.
  • It stays silent when it should. Genuinely incomparable givens remain an ambiguity error. Nothing is picked arbitrarily.

→Sequence

The work, in dependency order

The numbering is a real sequence: each phase names what must land before it.

  1. P0

    Make an exhausting implicit search terminate

    A query over equality constraints that cannot be satisfied already diverges on unmodified main. Today the first-success cutoff hides it. P1b removes that cutoff and makes it reachable from ordinary code.

    independent of specialization · worth doing on its own merits

  2. P1a

    The specificity filter

    Order the candidates that already reach the result set together — precisely the set that is an ambiguity error today. Cheap, safe, and the bulk of the payoff. Keep the existing depth cutoff. Split the penalties counter first: it currently charges for derivation shape as well as lexical distance.

    buys e1, e12, e14, lb

  3. P1b

    Reach candidates the depth cutoff hides

    Not a breadth-first continuation — e15 shows that is not viable. Instead, enumerate root givens by lexical stratum, order them, and try the maximal ones first. That bounds the extra work to one derivation attempt per root given and makes the algorithm provably agree with the declarative rule.

    needs P0 · buys e6, e15

  4. P2

    Specificity for overload resolution

    The same order, applied where two functions differ only in their context clause. This is what makes the familiar syntax work at call sites where the type is concrete.

    needs P1a

  5. P3

    Diagnostics that say why

    When candidates survive as incomparable, say so, and name the requirement that could not be derived — the entailment check already knows it.

  6. P4

    specializing fun

    Generate the algorithm-trait idiom instead of writing it by hand. A family of declarations differing only in their constraints desugars to a synthesized trait named after the function, one given per member, and a forwarder. Clients then opt into late binding with one token: <C is BidirectionalCollection & lower_bound>.

    needs P1 · this is the part that crosses a generic boundary

  7. P5

    The collection hierarchy in the standard library

    Greenfield — today's Core has no collection traits at all. Design it with P4 in hand rather than retrofitting.

  8. P6

    Blocked: running any of it

    Programs of this shape die in the LLVM backend on Runtime-defined IRWitnessTable operand. Type checking and IR are complete and correct — every result above was read off --emit ir — but nothing with a generic client and a conformance witness can execute yet.

    external · hylo-new#342

?Open

Decisions this raises but does not settle

Should refines desugar to a lifting given?

Today given Arr is RA {} fails unless the author separately supplies Bidi<Arr>. If refinement generated given <T is RA> => T is Bidi instead, conformance authors would write less, the coarse conformance would have a single derivation, and a third party could install a better witness for a whole class of types. The cost: a type that declares the coarse conformance itself then shadows the lifted witness wholesale, losing every refinement-level specialization at once. That argues for a companion feature — witness update syntax.

Should algorithm constraints be inferred rather than written?

P4 still asks the client to write & lower_bound. It could be inferred by fixpoint over the call graph, and there is a clean theorem behind it: if a witness is derivable from a function's declared context, adding it to that context never invalidates any call site, because the caller has already discharged that context — and the caller may supply a strictly more specific one. So propagation is always type-safe and can only improve specificity. The objection is that it makes a function's signature, and hence its module interface hash, depend on its body. Proposal: not in v1.

Does specificity outrank lexical proximity, or the other way round?

The prototype puts specificity first, which is what makes e6 work. But scoped overlapping conformances are a deliberate Hylo feature, and a conditional local override now loses to a more specific imported given. A context-free local given still wins, so the documented escape hatch survives. My reading is that this is an artefact of the conflated penalties counter rather than a real trade-off — but it should be decided explicitly, not inherited from a prototype.

Is there a role for monomorphization-time re-resolution?

It would recover C++ behaviour with no signature changes, but only as a best-effort optimization, and only if an algorithm's implementations are declared observationally interchangeable — the assumption C++ and GHC's SPECIALIZE both make tacitly. Worth a marker on the algorithm trait. Not v1.

The sharpest objection is completeness. State-of-Generics.md argues the smallest-term rule earns its place because it admits an algorithm complete with respect to a three-line declarative spec, so a user need only understand the spec. The specificity rule has to come with the same story — which is why the stratum-ordered enumeration in P1b is the load-bearing piece, not a refactor.

↩Prior art

Where this comes from

  • Siek & Lumsdaine, A Language for Generic Programming in the Large. The closest prior art. G has concept-based overloading with a most-specific rule, and §4.3 documents exactly the problem P4 solves — dispatching to an optimized algorithm from inside another generic function under separate compilation. G gave that case up; the witness-passing model gets it back.
  • Racordon, Flesselle & Pham, On the State of Coherence in the Land of Type Classes. Hylo's own position: reject global uniqueness, allow overlapping instances, disambiguate at the use site. A most-specific-wins policy is the natural completion of that stance, not a departure from it.
  • Rust RFC 1210. The chain rule, the default opt-in, and why the lattice rule was dropped — plus a decade of evidence that specialization tied to code generation is where the soundness problems live.
  • C++20 [temp.constr.order]. Subsumption as a partial order on constraints, decided without analysing types for equivalence.
