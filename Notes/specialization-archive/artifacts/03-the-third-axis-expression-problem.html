The Third Axis
A study · programming-language theory

The Third Axis

Wadler's expression problem has two axes: new data variants, new operations. Hylo's algorithm specialization needed a third — a way to add a better implementation of an existing operation for an existing type, chosen automatically. The literature has answered that third question twice before, for a dynamically-typed world and a monomorphized one. Neither answer fits a language that passes conformances as values.

axis 1 — new types (rows) axis 2 — new operations (columns) axis 3 — new implementations, ranked by specificity (stack depth)
§1

The problem, as stated in 1998

Philip Wadler named it in a one-paragraph note to a mailing list, and the paragraph has outlived most papers written about it:

"The goal is to define a datatype by cases, where one can add new cases to the datatype and new functions over the datatype, without recompiling existing code, and while retaining static type safety." Philip Wadler, The Expression Problem, note to the Java Genericity mailing list, 12 Nov 1998

Two axes, four demands. You can add a data variant (a new kind of expression). You can add an operation (a new function over expressions). Neither should require touching or recompiling code that already exists. And the compiler should still catch a missing case — no casts standing in for a check the type system used to do.

Functional languages nail the second axis and miss the first: match makes a new function trivial, but every existing match needs a new arm the day someone adds a variant. Object-oriented languages have the mirror problem: a new subclass slots in without touching anything, but a new virtual method means editing every class in the hierarchy.

Zenger and Odersky sharpened the criteria in 2005 with the one that turns out to matter most for this study:

"Independent extensibility: it should be possible to combine independently developed extensions so that they can be used jointly." Christoph Zenger & Martin Odersky, Independently Extensible Solutions to the Expression Problem, FOOL 2005

Not just "can I add a row" and "can I add a column" in isolation — can two people, who have never spoken to each other, each add one, and have the results compose? That is the criterion this study will actually run against Hylo's design in §5, with numbers from two real modules rather than an argument.

§2

What every canonical solution assumes

The 2000s produced two solutions elegant enough to become the standard answers, one per paradigm — and both quietly assume something this study is about to break.

Object algebras

Oliveira and Cook showed that ordinary generics — no F-bounded polymorphism, no wildcards — are enough. An "algebra" is a factory interface parameterized over its own result type; extending the data side means extending the factory interface, extending the operation side means writing a new algebra implementation, and neither touches the other.

Data types à la carte

Swierstra's dual, on the Haskell side: represent a datatype as the fixed point of a coproduct of functors. New variants are new summands, combined with a :+: operator; new operations are new typeclass-dispatched folds over the functor. Same two axes, opposite direction.

The shared assumption

Both constructions guarantee, by how they are built, that every populated cell of the (type × operation) grid has exactly one definition. There is no notion of two different, both-applicable answers for the same cell. Dispatch is a lookup in a table that is already complete and unambiguous by the time you ask it a question — not a choice among candidates. Extending the classical expression problem never has to ask "which of these several implementations applies best," because the constructions make that question impossible to pose.

That is the assumption a third axis breaks. Once an operation can have more than one candidate implementation for the same type — one written for a coarse description of it, a better one written for a finer description — dispatch stops being a lookup and starts being a choice.

§3

A third axis, and where it has been solved before

This framing is mine, not the literature's

No paper treats "new types × new operations × new specialized implementations of an existing operation" as one combined problem. What follows borrows real, load-bearing precedent for the third axis on its own — from two settings that predate the expression problem's canonical solutions — and combines it with the first two axes myself. Say so plainly rather than dressing a synthesis up as a citation.

The axis itself, stated precisely: for a single (type, operation) cell, allow more than one candidate implementation, differing in how narrowly each describes the type, and require the system to select the most specific applicable one — or refuse, if none dominates the others. Two systems built exactly this, decades apart, for very different purposes.

Common Lisp's generic functions

CLOS orders applicable methods by each argument's class precedence list — most-specific-first — and if two methods tie for most specific, calling the generic function is a runtime error: message ambiguous. The order is recomputed by the dispatcher at every call, dynamically, over whatever methods happen to be loaded.

Predicate dispatch

Ernst, Kaplan and Chambers generalized method specificity to arbitrary boolean predicates in 1998, and stated the ordering rule in words that could describe Hylo's entails check verbatim:

"Predicate dispatching considers one method m1 to override another method m2 exactly when m1's predicate implies m2's predicate and not vice versa." Michael Ernst, Craig Kaplan & Craig Chambers, Predicate Dispatching: A Unified Theory of Dispatch, ECOOP 1998

What they add that CLOS does not: static completeness and uniqueness checks, proved once at definition time, that guarantee no call site can ever hit the runtime "ambiguous" or "not understood" error. That guarantee is the benchmark the rest of this study measures against, and it is the one place Hylo's design falls short — see §6.

C++ partial specialization

The statically-typed, ahead-of-time analogue uses the identical implication-shaped rule — synthesize fictitious arguments for each specialization, convert both to function templates, and ask which one the other's arguments could deduce ([temp.class.order], [temp.func.order]). The difference is where the question gets answered: partial ordering is resolved at the point a specialization is selected for instantiation — structurally the same moment as monomorphization. A specialization not visible in the translation unit doing the instantiating simply does not exist for it; two translation units that disagree do not get an error, they get an ODR violation.

Four systems, one ordering rule, four very different guarantees.

§4

The combined model

Put the two classical axes and the third one in the same frame: a grid of (type, operation) cells, where each cell holds not one definition but a set of candidates ordered by specificity, and dispatch means finding that set's maximum.

A clean reduction

The classical expression problem is exactly this generalized one, restricted to the case where every cell holds at most one candidate. When a cell can hold more, the design needs three new things a single-candidate world never had to build: a specificity order over candidates (the entailment rule shared by §3's three precedents), a rule for what happens when two candidates are incomparable (refuse, per predicate dispatch and CLOS — never guess), and — because axis 1 and axis 2 are already open across separately compiled modules — a way to evaluate that order without a whole-program view, which is precisely where C++ and predicate dispatch stop applying and Hylo's design has to do something new.

This also explains a term from earlier in this project's own research. Racordon, Flesselle and Pham's survey of coherence in type-class systems treats "global uniqueness of instances" — Haskell, Swift and Rust's shared answer to overlapping conformances — as a design stance in its own right. Under this frame it is simpler than that: global uniqueness is exactly the assumption that every cell has depth at most one, asserted for a system that, unlike CLOS or predicate dispatch, never intended to have a third axis at all. Coherence is axis-3-depth-one, wearing different clothes.

§5

Scoring Hylo's design, axis by axis

Hylo fills the grid with three mechanisms, one per axis, each already measured in this project's compiler work:

  • Axis 1, new types — a downstream module declares given MyArray is RA {}. Ordinary trait conformance; the library never sees the type.
  • Axis 2, new operations — either a plain overload (closed: bound at the caller's own constraints, cannot cross into a generic function that does not name it) or an algorithm named as its own trait (open: anyone can add a given for it, exactly the object-algebra move).
  • Axis 3, new implementations — the specificity order from §3, adapted to Hylo's witness-passing rather than instantiation.
AxisNew cases addableNo modification of existing codeStatic type safetyIndependent extensibility
1 · types yesyesyesyes
2 · operations (open shape) yesyesyesyes
2 · operations (closed shape) yesyesyesno
3 · implementations yesyesyespartial

The closed shape's "no" is structural, not measured this session: a plain top-level fun is not an open extension point the way a trait is — its overload set belongs to the scope that declares it, and nothing lets a downstream module add a case to somebody else's function the way it can add a conformance to somebody else's trait.

Axis 3's "partial," with numbers

This is the one worth showing rather than asserting. Two independent modules, Collections and Turbo, each add a given for the same random-access case: 

// Collections.hylo          // Turbo.hylo (a different author, imports Collections)
given binary_search:            given turbo_search:
  <T is RA> => T is LowerBound   <T is RA> => T is LowerBound

A client importing both:

error: multiple given instance of 'LowerBound<MyArray>' in this scope
  note: candidate given is declared here     Collections.hylo:10
  note: candidate given is declared here     Turbo.hylo:2
  note: neither candidate is more specific than the other,
        so no choice can be made between them

Composition can fail — that is the honest half of "partial." But it fails the way Zenger and Odersky's criterion, taken seriously, demands it fail if it must fail at all: loud, naming both candidates, localized to the one client that imported both, and locally repairable — the client adds one given with a concrete head and the conflict is gone for its own code. Nothing is silently picked. That is a materially different answer from Hylo's own coherence study's verdict on Haskell, Swift and Rust, all three of which either reject the two definitions outright (closing axis 3 to third parties) or leave the choice to link order.

§6

What is actually new here

No single piece of this is new. The specificity order is predicate dispatch's, named in 1998. Resolving it statically and safely is what type classes have done for decades. Open, separately-compiled extension is the entire point of every expression-problem solution since Cook's. What is specific to combining them for Hylo is a point in a space no one precedent occupies alone: open across separately compiled modules, resolved statically with a named refusal rather than a runtime ambiguity, and requiring no global-uniqueness assumption — open like CLOS, static like predicate dispatch and C++, but without either predicate dispatch's closed-world view or C++'s reliance on a single instantiation site.

The gap this leaves open

Predicate dispatch's completeness and uniqueness checks prove, once, that no call site can ever hit an ambiguity or a missing case. Hylo's design has neither proof — it discovers ambiguity at each use site, the way CLOS discovers it at each call, just earlier: at compile time instead of run time. That may not be a gap this design can close, not just one it has not gotten to yet. Predicate dispatch's proofs work because the set of predicates is fixed and known when the check runs. Openness is precisely what Hylo's design keeps that predicate dispatch gives up — and completeness, in the classical sense, may need a closed world to even ask the question. Whether a weaker, still-useful completeness guarantee survives under separate compilation is the real open problem this study leaves on the table, not an implementation detail to fill in later.

Recap

Five sentences worth keeping

  1. The classical expression problem has two axes and one hidden assumption: every (type, operation) cell has at most one definition.
  2. A third axis — several candidate implementations per cell, ranked by specificity — has real precedent, but only ever solved half of what this project needed: CLOS is open but dynamic, predicate dispatch is static but closed-world, C++ is static but tied to a single instantiation site.
  3. Hylo's design is the first point in that space that is open, static, and requires no global-uniqueness assumption, all three at once.
  4. Measured directly: independent extensions can still conflict, but the conflict is a named, localized, compile-time refusal — never a silent pick.
  5. What it does not have, and may not be able to have without giving up openness, is predicate dispatch's proof that no such conflict can occur before anyone hits one.
