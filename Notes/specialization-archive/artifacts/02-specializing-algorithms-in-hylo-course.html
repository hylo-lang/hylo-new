Lesson 01

Why the obvious approach fails

In C++, specialization is a compile-time affair. Templates are instantiated per type, overload resolution happens after instantiation, and the compiler picks the best advance for the iterator it actually has. Hylo cannot do this, and the reason is worth understanding before anything else.

Hylo compiles a generic function once. It does not stamp out a copy per type. Instead, the conformances a function requires arrive as runtime values — witnesses — passed in like any other argument. Here is a generic function in Hylo's IR: 

fun search(_:)<T>(let %p0: LowerBound<T>, let %p1: T, set %p2: Int32) {
  %r0 = property "run" of %p0 as ... -> Int32
  %r3 = apply %r0(...)
}

%p0 is the witness. The function calls run through it. There is no copy of search for arrays and another for lists — there is one function, and what varies is the value it is handed.

The consequence

Specialization cannot be a code-generation trick, because there is no per-type code to generate. The specialized implementation has to be reachable from a witness that somebody hands the function. Everything else in this course follows from that one sentence.

That sounds like a limitation. It is actually the feature: because the choice is a value, it can be made where the type is known and then travel inward through as many generic layers as you like — no monomorphization, no code duplication. The whole design is about arranging for the right value to be chosen in the right place.

Lesson 02

The rule: applies to fewer types wins

Suppose Arr is both bidirectional and random-access, and two implementations are in scope: 

// the generic one — a linear scan
given linear_scan:   <T is Bidi> => T is LowerBound { fun run() -> Int32 { 1 } }
// the specialized one — a binary search
given binary_search: <T is RA>   => T is LowerBound { fun run() -> Int32 { 2 } }

Both apply to Arr. Both derivations are the same size — each is one step away from a conformance Arr declares directly. So size cannot tell them apart, and before this work the compiler simply reported an ambiguity.

The definition, precisely

Write a given as ∀X̄. C̄ ⇒ H — type parameters, requirements, and the conformance it produces. Then:

g is at least as specific as h when h's head can be instantiated to g's head, and every one of h's requirements is derivable under g's assumptions. g is strictly more specific when that holds one way and not the other.

This is C++20's concept subsumption and Siek & Lumsdaine's "callable from", transposed onto givens. Two things follow that are easy to get wrong:

  • It is not "more constraints wins." A given with no requirements but a head of LowerBound<Arr> beats one requiring T is RA, because it applies to one type rather than a family. Head and requirements are judged together.
  • It is a partial order. Two givens constrained on unrelated traits are incomparable, and the compiler refuses to guess. That refusal is the design working, not failing — see Lesson 6.

One order therefore covers the whole chain you would want: Array ≺ RandomAccessCollection ≺ BidirectionalCollection — a more concrete head and a finer requirement are ranked by the same definition.

Lesson 03

Where the choice happens

Here is the single most important thing to internalise: the implementation is chosen from what the enclosing context knows about the type, and from nothing else. Not from what the value really is at runtime. Not from what the caller knows.

You can watch this directly. Give the algorithm trait a type member that names the chosen implementation, then ask for it in three different contexts: 

trait LowerBound { type Selected }
given <T is Bidi> => T is LowerBound { type Selected = Linear }
given <T is RA>   => T is LowerBound { type Selected = Binary }

fun in_bidirectional_context<T is Bidi>(x: T.Selected) -> Linear { x }
fun in_random_access_context<T is RA>  (x: T.Selected) -> Binary { x }
fun at_concrete_type          (x: Arr.Selected) -> Binary { x }

All three type-check. Inside a function that knows only T is Bidi, T.Selected is Linear — the specialized implementation is not merely unused, it is unreachable. Add one fact to the context and the answer changes.

Why this assertion is honest

Selecting a type member forces resolution to commit to one witness, and unlike an overloaded call it cannot be steered by the expected type. Flip Linear to Binary in the first line and the file stops compiling. That is how every test in this suite is written.

So how does the choice travel inward?

Lesson 04

Three shapes an algorithm can take

Everything above leaves you with a design choice. There are exactly three ways to write a specializable algorithm in Hylo, and they differ in who can extend them and whether specialization survives a generic boundary.

Shape 1 — plain overloads

fun lower_bound<C is Bidi>(in c: C, _ x: C.Element) -> C.Position { …linear… }
fun lower_bound<C is RA>  (in c: C, _ x: C.Element) -> C.Position { …binary… }

Familiar, and it works at any call site where the type is concrete. Overloads are ordered by the operands they accept, not by what they return. But a caller declared <C is Bidi> binds the coarse overload statically — this shape does not cross a generic boundary. G documented exactly this limit in 2008.

Shape 2 — the algorithm as its own trait

trait LowerBound { fun run() -> Int32 }
given linear_scan:   <T is Bidi> => T is LowerBound { … }
given binary_search: <T is RA>   => T is LowerBound { … }

fun search<T is LowerBound>(c: T) -> Int32 { c.run() }

This is the CopyRange idiom from Siek & Lumsdaine's G. It is fully open — anyone, in any module, can add an implementation — and the choice crosses generic boundaries. The price is that every intermediate function must name the algorithm in its constraints. The requirement is viral.

Shape 3 — a trait member, installed by a lifting given

trait Bidi { fun sort() -> Int32 { 1 } }   // default implementation
trait RA {}                                // note: NOT a refinement

given ra_is_bidi: <T is RA> => T is Bidi { fun sort() -> Int32 { 2 } }

fun sort_all<T is Bidi>(c: T) -> Int32 { c.sort() }

Here the algorithm lives inside the data-structure witness. A random-access type never gets a plain Bidi witness — it gets the lifted one, which carries the better sort. So sort_all, constrained only on Bidi, runs the specialized implementation. No viral constraints, no monomorphization. The catch is that you must own the trait, and the type must not conform to Bidi directly.

ShapeCrosses a generic boundary?Third parties can extend?Cost
1 · Overloads No — the caller's constraints decide Yes None. Familiar syntax.
2 · Algorithm trait Yes Yes — fully open Viral constraint on every intermediate function.
3 · Lifting given Yes No — needs the trait's author The type must not declare the coarse conformance itself.

A real standard library uses all three: shape 3 for the algorithms the collection protocols own, shape 2 for open extension points, shape 1 for everything called at concrete types.

Lesson 05

Across module boundaries

All of the above was one file. The interesting questions start when a library and its client are compiled separately. Each answer below was produced by building actual .hylomodule archives and reading the client's IR.

Can a client add a faster implementation for its own type?
YesAnd it wins over the library's.

Hylo has no orphan rule. A downstream module declares a given for the library's algorithm keyed on its own type, and because a concrete head applies to exactly one type, it is more specific than any trait-keyed given the library shipped. 

// Client.hylo
import Collections
public struct MyArray { … }
given MyArray is Bidi {}
given MyArray is RA {}
given my_array_tuned: MyArray is LowerBound { fun run() -> Int32 { 3 } }

public fun main() -> Int32 { search(MyArray()) }
// Client.ir — what main actually builds
fun main(set %p0: Int32) {
  %r0 = project my_array_tuned[]      ← not binary_search
What if the library ships a new, more specific implementation?
AdditiveClients opt in by conforming.

A library cannot name your types, so its specializations are always keyed on traits. Ship a finer trait and an implementation for it: 

// Collections v2
public trait Contiguous refines RA {}
public given branchless: <T is Contiguous> => T is LowerBound { … }

A client that does nothing is unaffected — it still resolves to whatever it resolved to before. A client that adds given MyArray is Contiguous {} and recompiles picks up branchless. Both verified.

The one thing to be clear about: the choice is baked into the client's compiled code, as the IR above shows. A library upgrade only takes effect when the client is recompiled. That is inherent to dictionary passing with separate compilation, and it is the same deal as any inlined constant.

I pass an Array<T> to a generic sort that expects a BidirectionalCollection. Does it use the random-access algorithm — without monomorphizing?
DependsOn how sort is declared. Two of the three shapes say yes.

What if my type conforms to both Bidi and RA? Can I still get the random-access implementation?
Yes— but only with shape 2. Shape 3 dies here, and it dies quietly.

This is not a corner case, it is the normal case: if the library writes trait RA refines Bidi, conforming to both is not optional. Declaring only the finer one is rejected — 

given MyArray is RA {}
error: no given instance of 'Bidi<MyArray>' in this scope

Shape 3 loses. Your own Bidi conformance has a concrete head, so it is more specific than the lifting given and shadows it — carrying the trait's default implementations. Nothing is ambiguous, so nothing is reported. You just silently get the slow path.

And the lifting given cannot rescue you by supplying the base conformance that refines demands: that is circular, and the cycle guard rejects it. So refines and shape 3 are mutually exclusive — which is the real reason shape 3 requires RA not to refine Bidi.

Shape 2 wins. When the algorithm is its own trait, it does not live in the Bidi witness, so shadowing that witness costs you nothing. Verified across a module boundary, with MyArray conforming to both: 

// Both3.ir
fun main(set %p0: Int32) {
  %r3 = project binary_search$existentialized[...]   ← the RA implementation

The catch is the one from Lesson 3, unchanged: the function you call must be constrained on the algorithm. A sort_all<T is Bidi> still gets the slow one, no matter how many traits your type conforms to. Conformances of the type are not what decides — constraints of the function are.

If you are stuck with a <T is Bidi> signature and a type that conforms to both, the only local escape is to declare a better Bidi<MyArray> given in the scope where it matters. It works, and it means writing the fast implementation out again — a workaround, not a fix.

Lesson 06

Where it breaks

Hazard 1 · Two modules, equally specific

This is the real multi-module risk, and it is not hypothetical. Two independent libraries each add an implementation for <T is RA>. Neither is more specific than the other. A client that imports both gets: 

error: no coercion from ... to ...
  note: multiple given instance of 'LowerBound<MyArray>' in this scope
  note: candidate given is declared here     Collections.hylo:10
  note: candidate given is declared here     Turbo.hylo:2
  note: neither candidate is more specific than the other,
        so no choice can be made between them
What this means for you

Hylo detects the conflict at the point of use, not at the point of definition — it has no orphan rules to prevent you writing the second one. So the failure lands on the client that imports both, which is not who created it. The fix is local and cheap: the client declares its own given with a concrete head, which is more specific than both and resolves the conflict for its own code only.

This is a deliberate position, not an oversight. Hylo rejects global uniqueness of instances, which buys scoped and overlapping conformances; the cost is that conflicts surface downstream. A most-specific-wins rule reduces how often that happens — most overlaps are now ordered rather than ambiguous — but it cannot remove it, and it must not: guessing between two incomparable implementations would be worse.

Hazard 2 · A direct conformance silently shadows a lifted one

In shape 3, if the client writes given MyArray is Bidi {} alongside given MyArray is RA {}, its own conformance is more specific than the lifting given, so it wins — and it carries the default implementations. The client loses every refinement-level specialization at once, with no diagnostic, because nothing is ambiguous. It is simply a different, worse witness.

What makes this sharp rather than academic: a trait declared with refines forces exactly this. Hylo requires each conformance to a refined trait to supply a witness for the base, and the lifting given cannot supply it — that would be circular. So the moment a library writes trait RA refines Bidi, shape 3 is off the table for every client of it.

Two things would fix this, and neither exists yet. A way to derive a witness from another and override part of it, instead of all-or-nothing. Or — better — making refines generate a lifting given rather than demanding a base witness per conformance, so that "conforms to both" stops being something you are pushed into.

Hazard 3 · Specificity outranks lexical distance

When two candidates are incomparable, the lexically closer one wins. But specificity is consulted first, so a conditional given you declare locally no longer overrides a more specific one from an imported module. A local given with a concrete head still wins, because it is maximal — the documented escape hatch survives, the conditional one does not. I tested the alternative ordering; it breaks refinement chains outright.

Still missing

  • The boilerplate. Shape 2 is written by hand today. A specializing fun declaration could generate the trait, the givens and the forwarder, and let clients opt in with <C is BidirectionalCollection & lower_bound>.
  • Equality-constrained specialization. A given guarded by where T.Position == Int32 applies to nothing, because Hylo cannot yet derive that equality from a conformance that defines type Position = Int32. This predates the work here.
  • Running any of it. The LLVM backend cannot yet lower a generic client that takes a conformance witness. Everything in this course was verified at the IR level, which is where the choice is visible — but these programs do not execute yet.
  • A bounded search, not a complete one. Resolution is cut off by a work budget as well as a depth limit, because reasoning about equalities can derive the same goal along hundreds of thousands of paths. Answering each goal once and sharing the answer is the proper fix.
Recap

The five sentences worth keeping

  1. Hylo compiles a generic function once and passes conformances as values, so a specialized implementation must be reachable from a witness somebody hands in.
  2. More specific means applies to fewer types — head and requirements judged together — and where that does not order, nothing is chosen.
  3. The implementation is picked from what the enclosing context knows, so specialization crosses a generic boundary only if the algorithm is something the function receives.
  4. Constrain on the algorithm (open, viral) or put it in the data-structure witness (closed, invisible) — both avoid monomorphization; constraining on the data structure alone does not specialize.
  5. Clients can always specialize for their own types and always win; conflicts between two libraries surface at the client, and the client fixes them locally.
  6. If your type conforms to both the coarse and the fine trait — which refines forces — use shape 2; shape 3 loses silently there.
